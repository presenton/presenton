# P18. Параллельная генерация слайдов без барьера батчей + ретрай 429/5xx

Статус: закрыта, ветка `perf/parallel-slide-llm` (коммит 0dcd6090),
`make check` exit 0. В `main` не слита.

---

## Суть

Симптом от владельца продукта: генерация презентации дольше 10 минут при
загрузке CPU 20–30%. Диагноз по коду: конвейер I/O-bound (ожидание
LLM-провайдера), CPU ни при чём — «загрузить все ядра» неверная цель.
Реальные узкие места:

1. Слайды генерировались **последовательными батчами по 10**
   (`batch_size = 10`, `for start in range(...)` с `await gather` внутри) —
   деки больше батча сериализовались, вторая волна ждала самый медленный
   вызов первой.
2. **429/5xx от провайдера на слайдовых вызовах не ретраились** — один
   flaky-ответ валил всю генерацию (ретраились только «response_format
   violated»).

## Что сделано

1. **Семафор вместо барьера батчей** (`api/v1/ppt/endpoints/presentation.py`):
   все LLM-вызовы контента стартуют сразу, одновременность ограничивает
   `asyncio.Semaphore` с лимитом из env `SLIDE_LLM_CONCURRENCY`
   (`utils/get_env.py`, default 10 — прежний размер батча ⇒ N≤10 ведёт себя
   как раньше, деки >10 перестают сериализоваться).
2. **Прогресс через reporter-задачу**: `created_slides/remaining_slides`
   коммитит отдельная `report_slide_progress()` — общая `AsyncSession` не
   используется из параллельных задач слайдов (конкурентные коммиты в неё
   небезопасны). Провал коммита прогресса не останавливает генерацию.
3. **Отмена хвоста при сбое**: если один слайд упал, остальные LLM-вызовы
   и задачи ассетов отменяются (раньше догорали, сжигая токены).
4. **Ретрай 429/5xx** (`utils/llm_utils.py`):
   `_is_upstream_rate_or_server_error` (по `status_code`, фолбэк — текстовые
   маркеры «rate limit»/«too many requests»; fastapi `HTTPException` движка
   не ретраится), отдельный от schema-violation счётчик, паузы 1/4/8 c,
   максимум 3.
5. **Наблюдаемость**: warning `[llm.slow_call] model=... duration_s=...`
   при вызове дольше `LLM_SLOW_CALL_WARN_SEC` (`utils/get_env.py`,
   default 30, 0 отключает).

## Замер

Локальный стенд (uv + sqlite, DeepSeek `deepseek-v4-flash`,
`DISABLE_THINKING=true`, стадия `stage=slides`):

- 14 слайдов, батчи: 48.9 c (волны 10+4);
- 12 слайдов, батчи: 22.4 / 34.8 c; семафор: 33.3 / 22.2 c.

На 12 слайдах разница в пределах шума латентности провайдера (±40%);
структурный выигрыш — для дек >10 слайдов (конвейер вместо суммы волн) и
надёжность (429 больше не роняет генерацию). Финальный замер — на проде по
`stage=slides done duration_s=` до/после деплоя.

## Тесты

- integration: лимит параллелизма (максимум одновременных вызовов контента
  == `SLIDE_LLM_CONCURRENCY` при 6 слайдах), порядок слайдов и число вызовов;
- unit: классификация 429/5xx (включая «не ретраим локальный
  HTTPException»), ретрай с капом, независимость счётчиков
  schema/rate-ретраев.
- `make check` exit 0 (ruff + pytest + npm test + eslint + tsc).

## Что не делалось (осознанно)

- uvicorn workers >1 — сломал бы модульный in-flight lock `/preview` и не
  нужен (процесс I/O-bound);
- параллелизация экспорта (Chromium-раннер и так отдельный процесс);
- включение генерации картинок.
