# Задачи: интеграция Presenton с Telegram

Наша зона ответственности — серверная часть (`servers/fastapi`) и веб-фронт
(`servers/nextjs`). Telegram-бот и Mini App пишет другой разработчик, его задачи
здесь не описаны (см. бриф для него).

Область v1: пользователь из Telegram генерирует презентацию и получает файл.
Редактирование внутри Telegram в v1 не делаем.

Задачи отсортированы по приоритету: сверху то, без чего бот не работает вообще,
снизу то, что можно сделать после запуска. Описаны на уровне «цель + суть»,
разбивка на микрошаги — в `PROGRESS.md` соответствующей задачи.

## Блок 1. Критический путь MVP

Без этих задач бот не может работать. Делать строго в этом порядке.

### P1. owner_id при асинхронной генерации — ЗАКРЫТА, бага нет

Проверялось подозрение: `owner_id` берётся из contextvar, который
`SessionAuthMiddleware` сбрасывает в `finally`, а асинхронная генерация
выполняется через `BackgroundTasks` уже после ответа — значит владелец мог не
проставиться.

Подтвердилось только то, что `finally` действительно срабатывает раньше задачи.
Но владелец при этом остаётся на месте: сброс действует на контекст middleware,
а фоновая задача выполняется в копии, ответвлённой до сброса. `owner_id`
проставляется корректно, правка кода не нужна.

Добавлен регрессионный тест `tests/unit/test_async_generation_owner_scope.py` —
поведение держится на неочевидном порядке, который легко «починить» и тем самым
сломать. Разбор механизма и все проверки — в `PROGRESS.md`.

### P2. Авторизация через Telegram — ЗАКРЫТА (docs/progress/P2-telegram-auth.md)

**Цель.** Пользователь, пришедший из Telegram, получает рабочий аккаунт без
регистрации, ввода логина и пароля.

**Суть.** Новый эндпоинт `POST /api/v1/auth/telegram`, принимающий `initData` от
Telegram Mini App. Проверяем подпись (HMAC-SHA256, ключ =
`HMAC(key="WebAppData", data=<bot_token>)`), проверяем свежесть `auth_date`.
По `telegram_user_id` находим или создаём `User` с `username = f"tg_{id}"` и
случайным паролем, затем выдаём обычную сессионную куку через существующие
`get_jwt_strategy().write_token()` и `_set_login_cookie()`.

Дальше вся система работает как есть: `SessionAuthMiddleware` не меняем,
изоляция данных уже обеспечена глобальным owner-скоупингом в
`services/database.py`.

**Важно.** Схему БД менять не нужно: `User.username` — уникальный
`String(128)`, `tg_<id>` в него ложится. Отдельная колонка `telegram_id` —
преждевременно, добавим если понадобится обратный поиск.

**Явно НЕ делаем.** Не даём боту один админский API-ключ `sk-presenton-` на
всех пользователей: `api/v1/auth/principal.py` требует для ключа
`is_superuser`, и тогда все презентации всех пользователей получат `owner_id`
администратора — изоляция исчезнет.

**Почему вторая.** Это единственное, что блокирует разработчика бота: без
эндпоинта он не может даже начать. Всё остальное для генерации уже существует.

**Готово когда.** Запрос с валидным `initData` возвращает куку; повторный
запрос того же пользователя не создаёт второй аккаунт; невалидная подпись даёт
401; пользователь видит только свои презентации.

### P3. Endpoint превью слайдов картинками — ЗАКРЫТА (docs/progress/P3-slide-preview-images.md)

**Цель.** Mini App показывает результат, не поднимая тяжёлый редактор.

**Суть.** Бэкенд уже умеет рендерить слайды в PNG без браузера пользователя:
`EXPORT_TASK_SERVICE.render_jsons_to_images` (используется в
`templates/v2/tools.py`). HTTP-эндпоинта поверх этого нет.

Нужен endpoint, отдающий превью слайдов презентации картинками. Это позволяет
Mini App обойтись без `konva`, `tiptap`, `recharts` и `@babel/standalone`.

**Почему третья.** Формально бот может работать и без превью — отдавать сразу
файл. Но тогда Mini App нечего показывать, и разработчик либо тянет весь
редактор (чего мы договорились не делать), либо ждёт нас. Формат согласовать до
реализации.

**Готово когда.** Endpoint отдаёт превью слайдов существующей презентации,
доступ скоупится по владельцу, формат согласован с разработчиком Mini App.

## Блок 2. Нужно до открытия для пользователей

MVP технически работает и без этого, но выпускать наружу нельзя.

### P4. Квоты на генерацию по пользователям — ЗАКРЫТА (docs/progress/P4-generation-quota.md)

**Цель.** Один пользователь не может выжечь общий LLM-бюджет.

**Суть.** В проекте квот нет вообще. `ProviderSettings` — синглтон (`id=1`),
то есть LLM-ключи общие на всех пользователей, а `limit_req_zone` в
`nginx.conf` ограничивает только `/api/v1/auth/login`. При открытой регистрации
через Telegram это открытый кран.

Нужны: хранение лимита и потребления по пользователю, проверка перед запуском
генерации (синхронной и асинхронной), внятная ошибка при превышении и endpoint
для чтения остатка.

Начать с простого счётчика генераций за период (сутки/месяц) с дефолтом из
переменной окружения и возможностью переопределить лимит конкретному
пользователю. Учёт токенов и стоимости — позже, если понадобится.

**Почему здесь.** Пока идёт тестирование в узком кругу — терпимо. В момент, когда
бот открывается наружу, это самый дорогой из возможных пропусков: счёт приходит
сразу, откатить нельзя.

**Готово когда.** При исчерпании лимита генерация отклоняется понятной ошибкой;
остаток читается через API; лимит конкретного пользователя можно изменить.

### P5. Кука, работающая в Telegram-iframe — ЗАКРЫТА (merge c8c97f44)

**Цель.** Сессия не теряется при открытии Mini App на `web.telegram.org`.

**Суть.** `_set_login_cookie()` в `api/v1/auth/router.py` жёстко ставит
`samesite="lax"`. В мобильных клиентах Telegram Mini App — top-level WebView,
там Lax работает. В веб-клиенте Telegram это кросс-сайтовый iframe, куда браузер
Lax-куку не отдаёт. Нужен режим `SameSite=None; Secure` для этого сценария.

`X-Frame-Options` и CSP `frame-ancestors` в проекте нигде не выставлены, так что
само встраивание в iframe блокировать нечему — правка нужна только по куке.

**Почему не в первом блоке.** Правка на несколько строк, но проверить её без
HTTPS-домена невозможно, а домен — на стороне разработчика Mini App. На
мобильных клиентах Telegram (это большинство) всё работает и с текущей Lax.
Делаем, когда появится домен.

**Зависимость.** HTTPS-домен, внешняя.

**Статус.** Сделано в `b0076711` (merge `c8c97f44`, десктоп-Telegram): в
`_set_login_cookie()` при https-запросе (по `X-Forwarded-Proto` за прокси)
кука ставится `SameSite=None; Secure`, на локальном http остаётся `lax`.
Живая проверка в веб-клиенте Telegram — в рамках T-09 (нужен домен).

## Блок 3. После запуска

Не блокирует MVP, улучшает качество.

### P7. Надёжность вебхуков — ЗАКРЫТА (docs/progress/P7-webhook-retries.md)

**Цель.** Бот не теряет готовую презентацию из-за одной неудачной доставки.

**Суть.** В `services/webhook_service.py` ошибки доставки проглатываются
(`print` + `pass`), ретраев нет. Если бот на секунду недоступен — уведомление
потеряно навсегда, а пользователь остаётся ждать.

Минимум: несколько повторов с возрастающей задержкой и логирование результата
вместо `print`. Полноценная очередь не нужна — у бота есть страховка через
поллинг `/api/v1/async-tasks/{id}`.

**Почему не раньше.** Разработчику бота сказано делать поллинг как основной
механизм, а вебхук — как ускорение. Пока поллинг есть, потеря вебхука не теряет
данные, только замедляет ответ.

### P14. Обход 400001 от b.ai: флаг LLM_STRUCTURED_OUTPUTS — ЗАКРЫТА

**Симптом.** Генерация через TG-бота падает на шаге структуры презентации:
b.ai отвечает `HTTP 400, code 400001` — «response_format type is unavailable».
Подробности и диагностика — `docs/engine-response-format-issue.md`.

**Суть.** Модель b.ai не поддерживает `response_format` (`json_schema`).
Добавлен env-флаг `LLM_STRUCTURED_OUTPUTS` (default `true`); при `false`
движок не шлёт `response_format` ни в одном LLM-запросе
(`get_generate_kwargs` + `templates/v2/generation.py`) и парсит JSON из
текстового ответа (фенсы/проза снимаются в `extract_structured_content`,
schema-фидбек-луп сохранён). На сервере: `LLM_STRUCTURED_OUTPUTS=false` в
`.env` + перезапуск контейнера.

**Готово когда.** Генерация из бота проходит без `400` на
`chat/completions`; `make check` зелёный.

## Блок 4. CI/CD и инфраструктура

### C1. Деплой на сервер (yarexlab.ru) через GitHub Actions — ЗАКРЫТА (docs/progress/C1-deploy-github-actions.md)

**Цель.** Деплой движка на сервер — одна кнопка/мерж в main, без ручного SSH.

**Текущее состояние.** На сервере один контейнер из `docker-compose.server.yml`
(build на месте, порт `127.0.0.1:50521`, TLS на nginx хоста). В GitHub Actions
есть только апстримовские workflows: `test-all.yml` (тесты), `docker-release.yml`
(пушит образ в `ghcr.io/presenton/presenton` — чужой registry, на релизы),
`sync-releaes-to-r2.yml` (десктоп-релизы Presenton, нам не нужен). Деплоя нет.

**Подзадачи.**

- C1.1. Определиться со способом доставки образа:
  (a) build в CI → push в `ghcr.io/<owner>/yarex` → на сервере compose
  `pull && up -d` (рекомендуется: сервер не собирает, деплой быстрый,
  есть откат на предыдущий тег);
  (b) SSH → `git pull` → build на сервере (проще, но сборка на проде).
- C1.2. `deploy.yml`: job build (+ пуш образа при варианте a), job deploy
  по SSH (`appleboy/ssh-action` или ssh + secrets).
- C1.3. Secrets в GitHub: `DEPLOY_SSH_HOST`, `DEPLOY_SSH_USER`,
  `DEPLOY_SSH_KEY` (deploy-key с правом на репо/хост), при (a) —
  `GHCR_TOKEN` для pull на сервере.
- C1.4. `docker-compose.server.yml` под выбранный вариант: `image:` с тегом
  вместо/вместе с `build:`, фиксация тега деплоя (sha), `.env` на сервере
  без изменений.
- C1.5. Триггер деплоя — только `workflow_dispatch` (кнопка в Actions);
  автодеплой из main отключён. Окружение `production` с approval не нужно.
- C1.6. Post-deploy smoke: `curl` health-эндпоинта движка + внятный фейл
  workflow'а при недоступности; откат = redeploy предыдущего sha.
  После успешного деплоя — чистка старых образов на сервере
  (`docker rmi` прошлых `main-<sha>` + `docker image prune`).
- C1.7. (Заодно) добавить `npx tsc --noEmit -p tsconfig.codex-check.json`
  в `test-all.yml` — сейчас гейт есть только локально в `make check`.
- C1.8. (Заодно) удалить/почистить апстримовские workflows, которые нам не
  нужны (`sync-releaes-to-r2.yml`; `docker-release.yml` — заменить на наш
  build в ghcr.io/<owner>/yarex).

**Готово когда.** Мерж в main (или ручной dispatch) доезжает до
yarexlab.ru новой версией контейнера без ручного SSH; неудачный деплой
виден в Actions и откатывается.

## Блок 5. Редактирование из Telegram Mini App (v2)

Пользовательский путь v1 заканчивается файлом в чате; правки деки — через
веб-редактор движка по ссылке. Решение владельца: редактирование целиком в
Mini App через REST движка, внешняя ссылка редактора из UI убирается.

### P15. Редакторский REST (слайд-операции, editor-view/ops, превью-refresh) — ЗАКРЫТА

**Цель.** Mini App может править презентацию без полной перезаписи набора
слайдов (PATCH /presentation/update пересоздаёт все строки) и без «сырого»
редактирования ui-JSON.

**Суть.** Добавлены маршруты (все owner-scoped, cookie-сессия):
слайд-операции (`/slides/{id}/duplicate`, `DELETE /slides/{id}`,
`POST /presentation/{id}/slides` — пустой или по заготовке из каталога,
`PATCH /presentation/{id}/slides-order`, `GET /presentation/{id}/layout-catalog`);
редакторские проекции (`GET /presentation/{id}/editor-view`,
`PATCH /presentation/{id}/editor-ops` — move/resize/set_text/set_style/
set_image_url/delete/duplicate/reorder_element с валидацией и атомарностью);
`POST /presentation/{id}/preview` получил флаг `refresh` — пересборка PNG из
текущего состояния деки (правки не трогают старый PPTX, кэш по mtime был бы
устаревшим).

**Готово когда.** `make check` зелёный; тесты: integration
`test_deck_editor_api.py`, unit `test_deck_editor_service.py`, refresh-превью
в `test_slide_preview_endpoints.py`. Детали — `docs/progress/P15-deck-editor-api.md`.

### P16. Редакторские расширения для Mini App: undo-снимки, add_element, данные — ЗАКРЫТА

**Цель.** Mini App canvas второго поколения: отмена/возврат, добавление
элементов «с нуля», редактирование данных графиков/списков, rich-text.

**Суть.** `PATCH /presentation/{id}/editor-state` — полная замена ui слайда
(клиент хранит снимки ui из ответов); editor-view/editor-ops возвращают `ui`;
новые editor-ops: `add_element` (text/image/rectangle) и `set_data`
(text-list items, chart categories/series); `set_text` понимает
`**жирный**`/`*курсив*`/`<latex>` — парсер разметки вынесен в
`utils/template_text_runs.py` (был приватным в presentation.py); в
editor-view появились `complex`-предпросмотры (списки/графики).

**Готово когда.** fastapi 887 passed (unit/integration, в т.ч. HTTP
add_element и editor-state), ruff чист. Детали — docs/tg/04-editor-api.md.
